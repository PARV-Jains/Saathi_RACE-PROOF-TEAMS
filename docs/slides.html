PROBLEM STATEMENT & CHALLENGE

The Concurrency Dilemma: 50 Contenders for 1 Final Seat

Why naive database architectures fail and corrupt hackathon team rosters

❌ Naive Architecture (Disaster Mode)

  • Time-of-Check to Time-of-Use (TOCTOU): Multiple threads read count = 3/4 simultaneously outside transactions.
  • Oversold Team Roster: Both threads proceed to insert, creating 5 or 6 members in a team configured for maximum 4.
  • Phantom Duplicates: Double-clicking "Join" or flaky network retries creates duplicate teams and ghost records.
  • Stale UI Views: Users waste time requesting full teams because updates require manual page reloads.
Outcome: Corrupted database state, oversold seats, split-brain teams.

✅ The Saathi Concurrency Engine

  • Pessimistic Row Serialization: SELECT ... FOR UPDATE locks the team row exclusively at the database level.
  • In-Lock Capacity Validation: Capacity is evaluated strictly inside the lock. Exactly 1 transaction succeeds; 49 receive clean 409 Conflicts.
  • Atomic Idempotency Replay: Advisory locks and idempotency keys cache and replay results for retried requests with zero double mutations.
  • Instant Real-Time Sync: Server-Sent Events stream state mutations live across all connected clients with zero lag.
Outcome: Mathematical correctness, 0 oversold slots, 100% auditability.
CORE CONCURRENCY PRIMITIVES

Locking Invariant: SELECT ... FOR UPDATE

How atomic transactions serialize competing queries at the database storage engine level

// src/lib/team-service.ts — Atomic Transaction
await client.query('BEGIN');
// CRITICAL INVARIANT: Acquire exclusive row-level lock
const teamRes = await client.query(
`SELECT * FROM teams WHERE id = $1 FOR UPDATE`,
[teamId]
);
// Evaluate capacity STRICTLY inside the lock
if (team.current_member_count >= team.max_size) {
throw new AppError(409, 'TEAM_FULL', 'Team is already full');
}
// Increment count and record membership
await client.query(`INSERT INTO team_members ...`);
await client.query(`UPDATE teams SET current_member_count = current_member_count + 1 ...`);
await writeAuditLog(client, ...);
await client.query('COMMIT');
1. Exclusive Row-Level Queue

When 50 transactions request the same team ID, PostgreSQL queues 49 of them at the row lock. Only one proceeds at a time.

2. Zero Stale Read Windows

Capacity is never checked outside of the lock. When Transaction 2 unblocks, it reads the updated current_member_count = 4 and exits with 409 Conflict.

3. Database Schema Constraints

PostgreSQL enforces CHECK (current_member_count <= max_size) and unique hackathon participation indexes as a secondary defense layer.
